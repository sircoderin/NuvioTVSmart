# Continue the webOS performance work

Read [RESULTS.md](RESULTS.md) for the measured outcomes and limitations. The original code baseline is `358d08c` (upstream release 1.2.2). The tested TV is LG 43UQ70003LB, webOS 7.6.0, Chromium 87; OS version alone does not identify browser support or rendering capacity.

## Maintain the fork

Upstream 1.4.0 is merged into `webos-perf-refactor` (branch `merge-upstream-1.4.0`)
while retaining the fork policies below; 1.3.8 (`0604af9`) was the previous
merge and `8bd312df` is the last 1.2.4 fork commit. Upstream removed the Auto/Reduced/Full rendering setting, so the fork
keeps only the automatic constrained policy. Upstream's stream picker
re-checked `loadToken` before opening the player; the fork advances that token
on selection to cancel picker work, so the guard uses `playResolveToken`.
Early Home navigation was measured on this merge (RESULTS.md, "Upstream 1.4.0
merge on the TV"); the other historical results predate it. Experimental issue
candidates are excluded.

The intended Git layout is `origin` = `sircoderin/NuvioTVSmart`, `upstream` = `NuvioMedia/NuvioTVSmart`, and `webos-performance` = the custom build branch. Keep `main` aligned with upstream. Inspect `git status`, remotes, and the branch before starting; retain unrelated local edits.

To integrate an upstream update into a clean performance branch:

```sh
git fetch upstream
git switch webos-performance
git merge upstream/main
npm ci
npm run test:unit
npm run lint
npm run build
```

Resolve conflicts around the behavior below, then test on the TV before installing a newly merged build. A Git sync does not update the installed app. Avoid rebasing this published branch unless all users agree to rewrite its history. Prefer sending broadly useful fixes upstream to reduce the fork's long-term patch set. Fork setup/pushing was authorized in the originating session; future agents should use the current user's task to determine authorization for publishing and deployment.

## Preserve these behaviors during merges

- `js/platform/tvRuntimePerformance.js`: webOS 2022/2023 selects constrained rendering without selecting legacy API fallbacks. Tests distinguish those concepts.
- `css/webos-perf-motion.css` (loaded after upstream's components; named outside upstream's `components-NN` numbering so merges do not collide): eliminate costly motion but explicitly reveal elements that relied on keyframes for opacity (parental warnings, loading identity/spokes, stream panel, library picker, PIN opening). Preserve menu closing/hidden states. Home row tracks have no 3D transform on constrained TVs, so they do not get one compositor layer set per row. Stream panels drop `backdrop-filter`, which re-filters the artwork behind them on every scroll frame, and use a more opaque background instead. The startup loading pill's spinner (`home-loading-status-spinner`) is the one animation kept: a transform on its own layer, so the compositor turns it without the main thread. Its key-latency cost on the TV is not measured yet.
- `css/webos-perf-stream-picker.css` (loaded last): dense stream picker. Upstream's Android TV sizing (wrapping 32 px titles, unclamped 24 px descriptions, 40 px row gaps) showed about two results per screen on the tested TV; this restores the fork's 25/19 px clamped cards.
- Player startup mute (method 30 `syncStartupGateAndParentalGuide`): the UI tick also clears the presentation mute once loading is hidden and startup is ready. Releasing only the audio gate left `video.muted` set for the whole title when loading hid first; a seek was the only other path that cleared it.
- Home: `expandedPosterMarkup.js`, helpers 02/15, methods 12. Allocate expanded art/layers on focus, preserve runtime-owned nodes through `homeDomUpdate.js`, and skip forced hero layout on constrained TVs. The existing constrained row preview limit is ten items, with horizontal pagination. `homeDomUpdate.js` keeps markup signatures only for rows (`data-row-key`) and cards; other elements are compared node by node. Serializing every element repeated each subtree once per ancestor.
- Modern Home catalog virtualization (`homeRowVirtualWindow.js`, `homeRowVirtualization.js`): constrained rendering mounts at most nine catalog/collection rows, independently of the data-fetch range. Continue Watching/upcoming and the hero remain outside this window. Two aggregate spacers preserve catalog height; measured heights, horizontal positions and rendered card counts are cached by row key without retaining detached rows. Preserve original `this.rows` indices in card metadata. D-pad navigation resolves the logical adjacent catalog before mounting its DOM; Back mounts the saved row before restoring focus. Local window shifts create only entering rows, retain overlapping DOM and rebind pagination/hydration. Set spacer geometry before restoring viewport scroll, then compensate only for newly measured heights; doing those in the opposite order double-scrolls pointer jumps. Capture metrics before cleanup hides Home. `finishVirtualHomeRowUpdate` restores scroll and measures only rows mounted since the previous update; renders that keep the mounted rows do no geometry reads. Full rendering and Classic/Grid keep the previous rendering paths. This is a trial with mixed TV latency results, not established native parity; see the virtualization checkpoint in RESULTS.md.
- Home boot snapshot (`homeBootSnapshot.js`, `homeBootSnapshotPaint.js`, `package-webos.mjs`): after renders settle with Home at the top, the app saves a static copy of its first screen (no ids, runtime focus/expansion classes, media, virtual spacers; blob: posters swapped back to their original URLs) with the root classes and theme variables. The packaged `index.html` sets `__NUVIO_BUILD_ID__` (hash of the staged bundle and CSS) and paints the copy in a `contain: strict` fixed overlay before `app.bundle.js` loads, which waits one frame for it. The paint is skipped for another build, another profile, a restorable non-Home resume route or a title deep link. Only launches that entered Home without a picker or sign-in save one; a launch showing the picker drops it. The live Home removes the overlay after its first visible poster loads (at most 1.5 s), any other screen removes it at once, and it expires after 30 s.
- Home catalog range (`homeCatalogWindow.js`, `loadData`, `loadHomeCatalogRange`): Home requests catalogs in display order and skips catalogs hidden on Home. It requests the first `getInitialCatalogLoadCount()` rows plus the hero's catalogs, then extends the range to `HOME_CATALOG_PRELOAD_ROWS` rows past the focused row (`ensureHomeCatalogWindowForNode`, called from `rememberMainRowFocus`) or when pointer scrolling nears the end (`ensureHomeCatalogWindowForViewport`). Background reloads keep the range already reached. While focus is on the last navigation row, renders are not deferred for input, so rows loaded ahead appear while a key is held. Skeleton rows for every catalog were measured and rejected: mounting 70 placeholder rows cost about as much as the real rows.
- Home deferred catalogs (`createHomeRowBatcher`): on constrained and legacy TVs, rows that arrive after the initial batch are published together every `HOME_DEFERRED_ROW_BATCH_MS`; the window starts at the first pending row, so a trickle cannot postpone it. The first catalog batch still renders row by row. Each range is requested at once: the page receives a response only between main-thread tasks, so a cap on requests in flight let each Home render hold back the next catalogs. `fetchCatalogRows` keeps a `concurrency` pool for other callers, and a superseded load (`shouldContinue`) stops starting requests. `refreshWatchedTitleState` requests a render only when the watched title ID set changes.
- Player methods 28/68/71: retain control button identity through pause/resume; update only changed contents; keep focus and overlay synchronization. Do not reintroduce duplicate renders after `togglePause()`.
- Player episode panel (methods 65–67): key moves update focus classes in place (`syncEpisodePanelFocusDom`, used instead of upstream's `updateEpisodeStreamFocus`); streams keep focus by `streamMergeKey`, and results are ignored while an episode switch is in progress; only structural changes rebuild the panel. Stream cards render in batches of `PLAYER_STREAM_CARD_RENDER_BATCH`, appended as focus or scrolling nears the end. Streams show per source with the first-ranked source focused until the user moves. Entering an episode reuses the stream search cache; Reload forces a refresh. The player Sources panel (methods 62–64) uses the same card batching (`getStreamCardRenderLimit`), and its CSS shares the episode panel's 520 px sizing in `components-45/46.css`.
- `streamBadgeRules.js` and `streamBadgeSettingsStore.js`: upstream 1.2.3 adopted this optimization, and the fork uses upstream's version. It prepares immutable snapshots, bounded result/rule caches, defensive badge copies, and correct invalidation. Only concatenated positive lookaheads starting with `.*`, without capturing/backreference behavior or a top-level alternative, use the anchored line optimization. Preserve original regex behavior for other patterns and line terminators.
- Stream methods 01/04/09/10: constrained lists virtualize above 20 streams with a smaller nearby window; prepare settings once per window; avoid bulk badge matching on source arrival; keep early results selectable while other sources load; preserve the selected stream's identity and filter focus during updates.
- Stream initial focus follows the top row until the user presses a direction key (`streamFocusUserMoved`), so a slower, higher-ranked source takes the first row and focus when it arrives. After the user moves, focus identity is preserved as above.
- Home route resume (`canResumeHomeWithoutReload`, methods 04/20): a preserved Home reloads in full on return only when the inputs it is built from changed, which the resume signature tracks (sync-sensitive settings, installed-addon fingerprint, catalog preferences, stored profiles). Otherwise it refreshes only Continue Watching and watched marks (`refreshHomeContinueWatchingAfterSync`) and runs the existing stale-catalog refresh (`refreshHomeCatalogsIfStale`). Other screens cannot change catalog rows; what they can change (playback progress, watched state from the poster menu or details) is what the Continue Watching refresh reloads. `catalogRepository` caches catalog responses for the session, so a full reload on return re-rendered the same catalog data. Switching to a different profile always reloads Home; re-selecting the active profile resumes it.
- Home catalog settings pull (`homeCatalogSettingsPayload.js`): report a Home change only when the payload this device would describe after applying the remote differs from the current one. Applying keeps catalogs the remote does not list after the remote order, in their local order. A remote list saved before some catalogs were installed otherwise flagged a change on every launch, and the startup sync reloaded all of Home about 6 s in.
- Profile selection paints locally stored profiles before the remote profile/lock pulls. Profile activation and the options dialog wait for those lock states, so PIN-locked profiles still require the PIN.
- `profileScopedStore` caches normalized envelopes by the exact stored text (`LocalStore.getRaw`). Returned profile values are clones and envelopes are shallow copies; keep normalizers pure.
- Simkl tracking (`simklSyncService.js`): the snapshot is parsed once per stored text, the watched projection is cached per entries array, anime id preference and profile (callers get copied items), and `findEntry` uses an alias index per entries array. Replace entries instead of editing them in place. `getRecent` resolves the tracking source once, not per history item. Opening a title read settings stores thousands of times before this.
- Launch snapshot handover (`releaseHomeBootSnapshotWhenPainted`, method 24): the snapshot stays until every on-screen live poster has painted (3 s cap, first key press releases it), and on-screen posters hydrated while it is up keep the url it already decoded instead of a rescaled copy. The `homeLoadingStatus.js` pill shows catalog progress during a cold (non-background) load and hides when that load's catalog range resolves or Home is left.
- Home artwork on leaving (method 30, router): a retained Home DOM keeps its posters and rescale workers until the DOM is discarded (upstream 1.4.0's rule, replacing the fork's 30 s timer), so Back repaints at once. Navigating to the player still releases them 800 ms later (`releaseRetainedHomeArtworkSoon`), and mount cancels that release; upstream dropped the mount call, so re-check it after merges. Do not restore the immediate release on every exit.
- Upstream 1.4.0 Home additions next to the fork's: row parking (`homeRowWindow.js`) is disabled while virtual rows are active, because virtual rows already unmount distant rows and parking would reset their saved track positions. Upstream's row markup cache moved into the shared `renderModernCatalogRows`, and only full renders pass it; a virtual window update prunes `renderedRowMarkups` to the rows that stayed mounted, since a full render sends an empty stand-in for any row it believes is mounted. The IndexedDB catalog snapshot is written when the first deferred range completes (forced) and throttled after later window ranges. The snapshot (`homeCatalogSnapshotStore.js`, version 2) stores each row once as one JSON string per record, without the addon fields every item repeats; reading back thousands of stored objects was what made the old read slow. Constrained TVs use it differently (`startsFromHomeCatalogCache`, methods 21): the first catalog batch still comes from the network and Home's first render is unchanged, then `showCachedHomeCatalogRows` adds the cached copies of every later catalog through `publishLoadedHomeRows` instead of requesting them. Only catalogs missing from the cache are fetched. A constrained TV reads the cache whatever its age (`maxAgeMs: Infinity`; other devices keep the 12 h limit), like Native Legacy, which discards its cache only for another build, account, profile or language. The read waits up to 8 s, because IndexedDB callbacks queue behind startup tasks and a miss means requesting every catalog. A cached start sets `lastHomeCatalogRefreshAtMs` to the cache's age and schedules `refreshHomeCatalogsIfStale` 15 s later; on constrained TVs that refresh fetches one catalog at a time, only after 2.5 s without Home key presses, records its time only when it completes, and saves the cache afterwards. The refresh fetches rows in screen order and passes its 15 min window as `maxAgeMs` to `catalogRepository.getCatalog`: the repository keeps every page in memory for the session, so without it a later refresh, including upstream's route-resume refresh, got back the pages it already had. While a constrained TV stays on Home, `startHomeCatalogRefreshChecks` calls the same refresh once a minute; it does nothing while the catalogs are fresh, Home is not current or the app is hidden. A cached start never saves the cache before that refresh, so the saved time stays the age of the oldest row. Don't render all cached rows at once in the first render: it took 0.9 s on the TV against 0.4 s for the first batch. Upstream's adaptive artwork policy (`tvPerformancePolicy.js`) resolves to the immediate 1600 px eviction on the constrained 2022 webOS set.
- Postponed Home renders (methods 20 and 22): a full render requested while keys are held runs as one long task when input pauses, so a background update should mount rows or patch in place instead. A catalog that misses the row timeout keeps its request, and the retry waits for it (a new request only if it failed). Retried rows go through `publishLoadedHomeRows`. A watched-set change adopts the new set without a render unless a mounted poster's badge changes (`adoptWatchedTitleIdsInPlace`).
- `addonRepository` caches its normalized profile-scoped envelopes by the stored text plus the stored profile list (inherited profiles map to profile 1). Callers that filter many URLs pass one `getAddonEnabledStates()` result to `isAddonEnabled(url, states)` instead of re-reading per URL.
- Startup backend requests (`httpClient.js`, `webosSupabaseProxy.js`): non-legacy webOS (Chromium 85+, 2022+) sends Supabase requests directly from the browser. Legacy webOS keeps the companion-service proxy, and one direct network failure moves the rest of the session to the proxy (safe reads replay through it; writes do not). The webOS service answers `supabaseProxy`/`safeHttpProxy` in-process without booting the media runtime, and `boot-guard.js` warms the service (`warmup`) only below Chromium 85. The stream badge image prerender in `app.js` waits for the startup sync, because its image-proxy `status` call boots the media runtime.
- Selection cancels picker work immediately using the load token, abort controller, and scheduled-render cleanup. The repository-owned search session can continue and reattach on return. Keep the resume lookup and stale-navigation token guard. Remote resume lookup can still delay the handoff; it does not mean the picker waits for all sources.

## Local checks and configuration

Use Node 22+ for the profiler (global WebSocket). `npm run test:unit` discovers the available `js/**/*.test.mjs` and `services/**/*.test.mjs` tests. The inherited `npm test` wrapper references two absent `tests/test-plugin-*.mjs` files; do not report that wrapper as passing. Run `node scripts/test-webos-plugin-forwarding.cjs` separately when plugin/service behavior changes; it opens a localhost server and checks the Node 8 service contract. TV JS services must remain compatible with the device runtime, independently of the development Node version.

Runtime service settings are private and absent from a fresh checkout. A default build may fall back to example/empty configuration. For a deployable package, use your ignored `local.properties`, or capture the installed app's static configuration with the profiler as described below. Captured configuration stays under `.cache/tv-performance/`, with owner-only file permissions. Never commit it, SSH device keys, raw profiles, screenshots, or installed bundles; they can contain private or signed URLs.

```sh
NUVIO_BUILD_CHROMIUM=87 NUVIO_LOCAL_PROPERTIES=.cache/tv-performance/tv-build.properties NUVIO_REQUIRE_LOCAL_PROPERTIES=1 npm run package:webos
```

The package is `space.nuvio.webos_1.4.0_all.ipk` since the 1.4.0 merge; check the current app version for future builds. `NUVIO_BUILD_CHROMIUM` (`scripts/buildTarget.mjs`) targets the TV's browser instead of Chrome 56: esbuild/core-js/autoprefixer targets rise, and the inset/math/color and flex-gap CSS fallbacks are skipped (on this build: core-js 165 → 104 KB, app 3,767 → 3,692 KB, CSS 599 → 518 KB). The packaged boot gate raises its minimum Chromium to match, so older TVs report unsupported. Package files are ignored. Installing replaces the running app and needs authorization from the current task.

## Measure locally without the TV

`npm run perf:local -- --build` builds for Chromium 87, stages the webOS app without an IPK (`package-webos.mjs --stage-only`) and launches it in Playwright's cached headless Chromium, identified as the TV's Chromium 87 so the constrained TV paths run. The CPU is throttled (`--cpu`, default 8x), network responses are recorded once under `.cache/perf-local/fixtures` and replayed with fixed latency, the app-update check is blocked, and a synthetic addon adds 60 Home rows built from recorded Cinemeta posters (`--catalogs`). One priming launch is followed by `--runs` warm relaunches in the same browser profile; each reports first poster, interactive and settled times, long tasks, layout/style time and D-pad key-to-frame latency, saved under `.cache/perf-local/results/<commit>.json`. Use `--compare=FILE` for a before/after table, `--cpu-profile` for top self-time functions, `--screenshot`/`--screenshot-at=MS` to check what is on screen, `--no-snapshot` to A/B the Home boot snapshot, `--home-perf` for Home render counts and time, and `--early-keys` to start the keys as soon as Home is interactive instead of after it settles (at `--cpu=25` this reproduces the TV's early-navigation stutter; key latency is timed from the event's own timestamp, so time the key spent queued behind a long task counts). To compare two builds, stage each with `--build --save-app=NAME`, then run `--ab=OLD,NEW`: launches alternate between the two so machine drift (runs of the same build vary by 10–15% here) affects both equally; sequential before/after runs were misleading. The numbers compare builds on one machine; they are not TV timings, so confirm wins on the device. CPU throttling slows only the main thread: compositing and rasterization, which dominated Home browsing on the TV, are not modeled. Profiles from `--cpu-profile` attribute forced layout to the calling function; moving such a read without removing the layout it forces does not save time (hero description bounds, date formatting, sidebar focus checks and per-card settings reads were tried and made no measurable difference in an alternating A/B).

## Connect to the TV

Developer Mode and its SSH device configuration must already be available locally. Device aliases are machine-specific. Discover the current one rather than committing device credentials.

```sh
node node_modules/@webos-tools/cli/bin/ares-device.js --list
node node_modules/@webos-tools/cli/bin/ares-inspect.js -d 'DEVICE_ALIAS' space.nuvio.webos
```

Keep `ares-inspect` running. It prints a URL containing `?ws=localhost:PORT/devtools/page/TARGET`. The target/port changes after reinstall/relaunch. Set the matching WebSocket URL:

```sh
export NUVIO_CDP_URL='ws://127.0.0.1:PORT/devtools/page/TARGET'
npm run perf:tv -- --help
npm run perf:tv -- --ui-summary --player-state --cleanup-check
```

`--endpoint=ws://...` overrides the environment variable. Artifacts default to ignored `.cache/tv-performance/`; `--output-dir=PATH` overrides that directory. The profiler neither installs packages nor discovers SSH credentials. Use the locally installed CLI directly if the inherited npm inspect/install wrappers cannot find a global `ares-*` executable.

## Repeat the measured flows

Confirm the visible screen before acting. The UI summary reports active screens and visible focus; Home may remain mounted but hidden during playback. Allocated hidden DOM is not evidence that it continuously lays out. A dispatched click does not prove navigation or successful playback. Keep screenshots out of timed loops.

1. **Home navigation:** after Home has settled, focus Continue Watching and run `npm run perf:tv -- --measure`. This sends the same 16 right/left keys as the baseline, captures RAF intervals/long tasks/CPU samples, and exits 2 if p95 key-to-next-frame exceeds 100 ms or samples are incomplete. Handler timing is measured by capture listeners; the `--probe` window listener is better for keys stopped by the app.
2. **Search:** use visible sidebar keys or its selector to open Search. Run `npm run perf:tv -- --probe --type=abbott`. `--type` uses CDP text insertion, not the LG system keyboard; do not claim it measures the keyboard itself. Route opening must be included in a probe to measure it.
3. **Early streams:** from visible Home, run the command below. It selects the first available 720/1080-labelled card while skipping donation rows; check `pendingSources > 0`, then check `video.readyState=4` and nonzero dimensions. This is source-specific; a quality label cannot guarantee a playable codec/URL. Reset the app/search cache when a warm session would hide late-source behavior. Confirm Home is ready after reload before clicking.
4. **Pause/subtitles:** while real video is playing, run `npm run perf:tv -- --probe --press=MediaPlayPause,s,ArrowDown`. It pauses, opens subtitles, and moves focus without selecting a subtitle. Close the dialog afterward with `--press=Escape` and verify `--player-state` still shows paused video.
5. **Badge CPU:** `npm run perf:tv -- --badge-stats --badge-benchmark --baseline-ref=358d08c` compares the baseline/current pure matcher on the TV with its active rules and 24 synthetic descriptions. Confirm identical results. This isolates badge matching; it is not total stream-load time.
6. **Early Home navigation:** `npm run perf:tv -- --early-nav=LABEL` reloads the app, presses 8 Down, 6 Right and 8 Up keys 350 ms apart as soon as Home is interactive, and reports key latency from `event.timeStamp`, long tasks, and the Home renders that ran while keys were pressed (from the app's `[home-perf]` log). This is the window in which catalogs are still loading. Two runs per build are enough to see stalls of several seconds; reinstalling changes the build id, so let the new build save its boot snapshot (stay on Home at the top for about 10 s) before the first run. `--early-nav-profile` adds a CPU profile but slows the TV noticeably. In TV profiles, check the gaps between samples before blaming a function: the whole renderer stalls for 50–370 ms at a time, and the function on top at that moment receives the full gap.
7. **Visibility:** `npm run perf:tv -- --css-smoke` checks computed visibility of animation-dependent components on the constrained build. Expect opacity 1 and animation none for the tested open/visible elements.

```sh
npm run perf:tv -- --probe --click='.home-continue-card[data-item-title="Abbott Elementary"]' --early-play --wait=10000 --player-state
npm run perf:tv -- --capture-build-config
```

Historical benchmarks and snapshots vary with warm caches, loaded source counts, and startup timing. Compare the same route, focus, stream, settled state, and rule settings. Report the number of keys/sources/cards alongside timing rather than promising a universal speedup.

## Diagnostic experiments and completion

`--no-motion`, `--no-effects`, `--constrained`, and `--prune-rows` change the current TV session before actions/probes. `--prune-rows` temporarily detaches rows after the first six; it is a causal experiment, not the implemented Home architecture. Overrides persist between runs until explicitly restored. Run one profiler at a time. On normal completion or an action error, the script stops its timing observers/RAF loops; a disconnected inspector can prevent remote cleanup.

After any experiment:

```sh
npm run perf:tv -- --restore --cleanup-check --player-state
```

Completion means: relevant unit/lint/build checks pass; the original TV flow improves without breaking focus, resume, subtitles, or early selection; diagnostic cleanup reports no temporary styles, detached rows, active probes, or saved class override; playback is left paused when the task is done. Update RESULTS.md with the device, app/build, sample counts, and remaining limitations. Do not claim Stremio parity from these samples. The inspected reference was the public `Stremio/stremio-web` repository, not the LG application source.
